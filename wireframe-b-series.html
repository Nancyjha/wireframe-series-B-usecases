DB2 Buffer Pool BP0 undersized — root cause of PAYROLL01–04 S0C4 abend chain
Rule 94% · AI 91% · Combined 93%

BP0 sequential prefetch pages spiked from 412K (baseline) to 4.89M (×11.9) on 24 Sep. This is consistent with a recent SQL change in DSNPAYRL introducing full-table scans on a large table. Long sequential scan I/O holds row-level locks for the duration of each page read — at ×11.9 the lock hold time was long enough to cause 3 deadlocks at 22:14:20. DB2 rolled back the deadlocked transactions; PAYRLMN did not check return codes and proceeded to access freed storage, triggering S0C4 in STEP030. All 4 parallel PAYROLL jobs share the same plan and accessed the same table, causing all 4 to abend within 6 minutes.

Specific actions
  1. Immediate: Increase BP0 VPSIZE by 20–30% in DSNZPARM and restart the buffer pool (no DB2 recycle required).
  2. Root cause: Run EXPLAIN on DSNPAYRL to identify the full-table access path. Check the PAYROLL application change log for 22–24 Sep for SQL or schema changes. Add a missing index on the scanned table.
  3. Application fix: Review PAYRLMN source code for DB2 return code checking after FETCH/INSERT/UPDATE calls. Add SQLCODE check and graceful error handling for SQLCODE -911 (deadlock rollback).
  4. Monitor: Watch BP0 hit ratio and DSNPAYRL deadlock count for next 3 ingestion runs after the BP0 resize. If deadlocks persist, the missing index is still needed.
